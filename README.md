# 图表库多维度评测系统（Chart-Benchmark）开发计划方案

## 🛠️ 一、 项目定位与核心目标

打造一个可视化的图表选型与性能评测工具。通过**控制变量法**（相同数据源、相同硬件环境），横向对比国内外主流图表库（ECharts, Chart.js, Plotly, Seaborn 等），为开发者在**视觉效果、代码成本、渲染性能**三个维度提供直观的量化数据参考。

---

## 📐 二、 系统架构设计

系统采用**前后端分离**架构，以 Web 端作为统一的成果展示与性能监测面板。

```
[前端控制台 (Vite + React/Vue)]
    │
    ├──► 模块 A: 统一数据发生器 (Mock/流式/量化K线)
    ├──► 模块 B: 沙盒渲染看板 (ECharts / Chart.js / Plotly.js 并排联动)
    └──► 模块 C: 性能监测器 (FPS / 渲染耗时 / 内存堆栈)
    │
[后端评测引擎 (Python FastAPI)] ─── (可选，中后期接入)
    │
    └──► 评测 Python 库: Matplotlib / Seaborn / Pyecharts (返回渲染耗时与体积)

```

---

## 📝 三、 核心评测维度与指标定义

1. **渲染硬实力（Performance）**
* **Init-to-Ready Time（首屏耗时）：** 从调用 `.init()` 或数据传入，到 `requestAnimationFrame` 触发第一帧渲染完成的毫秒数（$\Delta t = t_{\text{ready}} - t_{\text{start}}$）。
* **FPS（帧率稳定性）：** 在大数据量下进行 Zoom（放大）和 Pan（平移）交互时，监听 5 秒内的平均帧率。
* **Memory Heap（内存增量）：** 渲染前后浏览器 `usedJSHeapSize` 的差值。


2. **开发软实力（DX - Developer Experience）**
* **代码行数（LOC）：** 实现标准功能（如带 Tooltip 的双 Y 轴折线图）所需的配置项/代码行数。
* **学习曲线：** 文档丰富度与社区活跃度（以 GitHub Stars 和 Issue 解决率为参考指标）。


3. **视觉与交互（UI/UX）**
* **响应式表现：** 容器尺寸平滑改变（Resize）时的重绘流畅度。
* **原生功能：** 是否自带图片导出、数据视图切换、区域缩放条（DataZoom）等。

## 📅 四、 实施阶段与时间表（4周敏捷开发）

### 🚀 第一周：基础设施搭建与数据管道（Data Pipeline）

* **目标：** 确立前端脚手架，完成数据发生器的编写。
* **交付物：**
* 基于 Vite + React/Vue + Tailwind CSS 的响应式基础布局。
* `dataGenerator.ts`：支持生成三种规格的数据：
1. **Lightweight（轻量）：** 100 条常规业务报表数据。
2. **Stress Test（高压）：** 10,000 ~ 200,000 条散点/折线数据（用作极限测试）。
3. **Financial K-Line（量化）：** 包含 Open/Close/High/Low/Volume 的标准股票行情数据。





### 🎨 第二周：前端沙盒组件开发（Web 库接入）

* **目标：** 实现第一批 Web 图表库的并排渲染与同步交互。
* **交付物：**
* 接入 **Apache ECharts** 和 **Chart.js**（可选加入 **Plotly.js**）。
* 开发高阶组件（HOC）包裹各图表库，利用 `performance.now()` 在组件生命周期内精准埋点。
* **联动联动功能（Sync Zoom）：** 监听某一图表的鼠标滚轮事件，通过 API 同步更新其余图表的 `dataZoom` 区间。



### 📊 第三周：性能监测面板与源码对比（Dashboard）

* **目标：** 完善 UI 界面，将枯燥的性能数据可视化，并加入代码对比。
* **交付物：**
* **实时仪表盘：** 使用简洁的仪表盘或柱状图，实时展示三个库的“首屏耗时”与“FPS 最低点”。
* **Code-Diff 面板：** 利用 `prismjs` 或 `monaco-editor` 并在右侧或抽屉组件中展示两者的 `option` 配置项源码，方便直观对比开发成本。



### 🐍 第四周（进阶）：Python 评测引擎扩展与总结

* **目标：** 引入 Python 后端，扩展对数据科学库的评测，完成项目上线。
* **交付物：**
* 搭建 **FastAPI** 服务端。
* 编写脚本让 **Matplotlib** 和 **Seaborn** 渲染相同的量化数据集，计算后端生成图片并传输的耗时。
* 优化前端界面，支持“前端渲染库”与“后端生成图”的综合对比报告。

## ⚠️ 五、 关键技术难点与解决方案

* **难点一：如何准确测量每个库的渲染耗时？**
* *原因：* 许多现代图表库的渲染是异步的（例如 React 包装库的更新延迟，或者 Canvas 内部的异步分片渲染）。
* *对策：* 不依赖组件的 `useEffect` 结束时间，而是直接深入原生库的事件钩子（如 ECharts 的 `finished` 事件），或者使用 `requestAnimationFrame(() => { // 此时渲染基本完成 })` 来截获时间戳。


* **难点二：大数据量直接导致浏览器卡死挂起。**
* *原因：* SVG 类型的图表库在 10 万条数据下会生成 10 万个 DOM 节点。
* *对策：* 在高压测试模块加入“熔断机制”或提示警告；同时开启图表库自身的降级策略（如 ECharts 的 `appendData` 流式渲染或开启 `large: true` 优化）。
